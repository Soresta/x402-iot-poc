# Unattended run, 2026-09-11

**Closes:** nothing fully. The W3 buyer DoD asks for 24 h and this is not 24 h.
**Raw log:** [`soak-2026-09-11.log`](./soak-2026-09-11.log). The run was stopped by
shutting the laptop, so the log has no `SOAK RUN END` block. Every figure below
comes from that log, `buyer/ledger.jsonl`, the seller's `/api/receipts`, and USDC
`Transfer` events read from Base Sepolia.

The machine was not running unattended for 24 hours. The honest description is
**about 2.5 hours of buying spread across 9 hours**, with the laptop asleep or
offline in between. The agent cannot tell sleep from a network outage. It saw
`fetch failed`, backed off, paused, and resumed when the machine woke. That
recovery is the part that did work unattended.

## Reconciliation: 147 on-chain, 146 in the ledger

Every ledger success matches an on-chain transfer, and 146 of the 147 transfers
match a ledger success. The remaining one:

```text
tx        0x5108354b069307601cbe0aebabe89ac90191c4ca1c6cb22231f3a0812ffc8093
on-chain  2026-09-11T16:49:20Z   1000 atomic USDC, buyer → seller
receipt   2026-09-11T16:49:18.815Z  (seller /api/receipts, resource: readings)
buyer     [agent] Paying $0.001 for sell-iot-reading (running total: $0.1010)
          [agent] Network error: fetch failed
```

The seller verified, served and settled the request. The response never reached
the buyer, which went offline at that moment — it is the first minute of the 4 h 26 m gap. The buyer
recorded nothing, so **its spending cap undercounted by one payment.**

This is not the "paid but undelivered" case withdrawn on 2026-09-11. That claim
was about the seller failing after settlement, which the middleware prevents. Here
the seller did its job and the client lost the answer. No seller-side check can
see that. The buyer has to assume the worst.

## What this changed

- **The buyer counts a payment whose response was lost.** A network error during
  the paid request is now recorded as `payment_unconfirmed`, and it counts against
  the cap. When the request never left the machine, this overcounts. For a cap,
  overcounting is the safe way to be wrong.
- **A second accounting bug, found while fixing the first.** `cap_reached` ledger
  entries carry the price the agent *refused* to pay, and the cap summed them as
  spend. The ledger holds eight. The cap now counts only `success` and
  `payment_unconfirmed`. This bug was also on the safe side (cap too strict), but
  it made the cap's figures wrong.
- **Soak runs write their own log file** under `docs/soak-runs/` instead of
  appending to the week 3 evidence.
- Regression test and mutation added. The suite is 73 tests.

## The `402 {}` refusals

In this run, 12 of 159 payment attempts were refused at settlement, 7.5%. The
morning's guess was concurrent payments from one wallet, and it does not survive
this run: the soak was the only buyer process. The on-chain count proves none of
the 12 settled. The cause is still unknown, because neither side logs the
facilitator's `errorReason`. That is the next thing to add, before anyone quotes a
reliability figure.
